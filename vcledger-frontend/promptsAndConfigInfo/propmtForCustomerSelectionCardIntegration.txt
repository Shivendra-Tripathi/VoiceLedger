I am developing the frontend of my **VcLedger** application using React. I want you to implement a **CustomerSelectionCard** for the Voice Ledger page.

## 1. Existing Architecture

The current `VoiceLedgerPage`:

* Records audio using a custom `useAudioRecorder` hook.
* Sends the recorded audio to the backend using `sendVoiceCommand(audioBlob)`.
* Receives a structured response from the backend.
* Displays responses in the upper ledger/conversation section.
* Currently, responses are rendered generically, but I now want to introduce a **scalable, registry-based architecture for interactive response components**.

The architecture must allow me to add many different interactive cards in the future, for example:

* `CustomerSelectionCard`
* `ConfirmTransactionCard`
* `CustomerBalanceCard`
* `TransactionHistoryCard`
* `DeleteTransactionCard`
* etc.

Do **not** implement this as a large `if/else` or `switch` directly inside `VoiceLedgerPage`.

---

## 2. Required Architecture

Use a **registry-based response rendering architecture**.

The conceptual flow must be:

```text
Backend Response
       ↓
response.type
       ↓
Response Registry
       ↓
Corresponding React Component
       ↓
Interactive UI
       ↓
User Action
       ↓
Backend API Request
       ↓
New Backend Response
       ↓
Registry renders the next appropriate component
```

For example:

```text
SELECT_CUSTOMER
       ↓
CustomerSelectionCard
```

Later:

```text
CONFIRM_TRANSACTION
       ↓
ConfirmTransactionCard
```

The `VoiceLedgerPage` should remain an **orchestrator**, not a component containing the implementation of every response type.

Create an appropriate structure such as:

```text
src/
├── components/
│   └── ledger/
│       ├── responses/
│       │   ├── CustomerSelectionCard.jsx
│       │   ├── ...
│       │
│       ├── LedgerResponseRenderer.jsx
│       └── ledgerResponseRegistry.js
│
├── api/
│   └── ...
│
└── pages/
    └── VoiceLedgerPage.jsx
```

You may modify this structure if you have a better scalable design, but explain the reason.

# 4. CustomerSelectionCard Requirements

Implement a reusable:

```text
CustomerSelectionCard
```

The card should:

1. Display the customers provided by the backend.
2. Clearly indicate that the user needs to select the appropriate customer.
3. Allow the user to select **one customer**.
4. Be fully interactive.
5. Use the customer's actual ID/value from the backend rather than relying only on the displayed name.
6. Handle the selected customer cleanly.
7. Send the appropriate request to the backend after selection.
8. Prevent duplicate submissions.
9. Handle loading state while the selection request is being processed.
10. Handle backend/API errors gracefully.
11. Be reusable for different situations where customer selection may be required.

Do not hard-code customer names.

# 6. Lock the Card After Selection

This is extremely important.

Once the user selects a customer:

```text
CustomerSelectionCard
        ↓
Customer selected
        ↓
Card becomes locked
```

After selection:

* The user must no longer be able to select another customer.
* Customer-selection buttons/options must become disabled.
* The card should visually communicate that the selection has been completed.
* The selected customer should remain clearly visible.
* The component must not accept another selection while the request is being processed.
* After the backend request succeeds, the component must remain locked.
* Do not allow double-clicks or duplicate API requests.

Conceptually:

```text
ACTIVE
  ↓
User selects customer
  ↓
SUBMITTING
  ↓
Backend response
  ↓
LOCKED
```

The locked state should be represented explicitly rather than relying only on incidental button disabling.

# 8. Registry-Based Architecture

Create a response registry.

Conceptually:

```js
const ledgerResponseRegistry = {
    SELECT_CUSTOMER: CustomerSelectionCard,

    // Future components:
    // CONFIRM_TRANSACTION: ConfirmTransactionCard,
    // CUSTOMER_BALANCE: CustomerBalanceCard,
    // TRANSACTION_HISTORY: TransactionHistoryCard,
};
```

Then create a generic response renderer:

```text
LedgerResponseRenderer
        ↓
looks at response.type
        ↓
finds component in registry
        ↓
renders corresponding component
```

Do not put the response-type logic directly inside `VoiceLedgerPage`.

The renderer should be generic enough that adding another response type requires primarily:

1. Creating the new component.
2. Registering it in the registry.

It should not require rewriting the entire Voice Ledger page.

---

# 9. Action Handling

Design the components so that interactive cards can communicate user actions back to the parent/application layer.

For example:

```text
CustomerSelectionCard
        ↓
onAction({
    type: "CUSTOMER_SELECTED",
    customerId: ...
})
        ↓
VoiceLedgerPage / application controller
        ↓
API service
```

Do not tightly couple `CustomerSelectionCard` to the entire VoiceLedger application.

The card should primarily be responsible for:

* rendering its UI
* managing its local interaction state
* reporting the user's action

The application layer should coordinate the larger workflow.

# 10. Scalability Requirement

This architecture must be designed assuming that the application will eventually contain **dozens of response types and interactive cards**.

Avoid:

```js
if (response.type === ...)
else if (response.type === ...)
else if (...)
```

inside `VoiceLedgerPage`.

Avoid a massive monolithic component.

Avoid duplicating API/request logic across components when it can reasonably be centralized.

The architecture should make this easy:

```text
New backend response
        ↓
New React card
        ↓
Register component
        ↓
Automatically render based on response.type
```
